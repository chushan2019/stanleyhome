模型厂商在发布时给出的榜单，适合用来做“能力雷达”和初筛，但**不应直接等同于你日常工作中的生产力**。对你这种重度使用 Claude Code/Codex、做真实项目开发、同时需要研究写作、结构化产出与内容制作的人，最有价值的做法是：先用少数榜单排除明显不适配的模型，再用一套“私有任务集 + 可复现评分规则 + 成本/稳定性记录”做最终选型。

## 先建立正确理解

每个 benchmark（基准测评）本质上都是：

> 给模型一套固定任务、固定输入、固定工具和固定预算，然后用一个预先规定的指标，计算成功率、准确率或偏好分。

因此它回答的从来不是“这个模型总体是不是最强”，而是：

> “在这个测试设定下，这个**模型 + 提示词 + Agent 框架 + 工具 + token/时间预算**的组合，完成这类任务的表现如何？”

尤其是 Agent 时代，厂商宣传的分数通常不是纯模型裸分，而是整个系统成绩。比如 SWE-bench 要求 Agent 接收真实 GitHub issue、在指定历史版本的完整仓库中定位问题、修改代码，并通过真实项目测试；它评估的是“端到端修复任务”的成功率，而不只是会不会写一段函数。SWE-bench Verified 则是其中经过人工核验、可解且测试有效的 500 道子集。 [swebench](https://www.swebench.com/verified.html)

所以看到一个模型“95% SWE-bench”时，正确问题不是“它是不是比 85% 的模型强 10 个点”，而是：

- 是哪个版本：SWE-bench、Verified、Pro，还是别的变体？
- 用的是什么 Agent scaffold：是否有规划、搜索、测试、反复修复、多 Agent？
- 是否允许工具调用、多少轮、多少 token、多久时间？
- 用了几次采样：pass@1、pass@k，还是挑最好的一次？
- 模型是否可能见过训练数据，或 benchmark 是否已饱和？
- 与我的代码语言、仓库结构、任务粒度、协作方式是否相像？

公开榜单的价值是“**候选池筛选**”；个人评测的价值才是“**决策依据**”。

## 常见榜单怎么读

下面按你最相关的工作类型来解释。重点不是记住名字，而是理解“测什么、不能说明什么”。

| 榜单/类别 | 主要测什么 | 对你的参考价值 | 不能直接推出什么 |
|---|---|---|---|
| SWE-bench / SWE-bench Verified | 在真实开源仓库中，根据 issue 修复 bug 或完成小型工程改动；以真实测试是否通过判定 | 高：适合判断“读仓库—定位—改码—测试—提交补丁”能力 | 不能代表从零搭项目、产品需求澄清、前端审美、私有业务架构能力 |
| SWE-bench Pro / 长程软件工程评测 | 更复杂、更接近多文件、多约束、较长链路的软件工程任务 | 很高：更接近复杂 feature、跨模块改造和真实 repo 协作 | 不代表你的 TypeScript/Python 栈一定同样收益，也受 Agent 框架影响很大 |
| Terminal-Bench | 在终端/CLI 环境中完成系统操作、脚本、排错、文件与命令行工作流 | 高：若常用 Claude Code、Codex、tmux、Git、CI、shell，这项很值得看 | 不代表 IDE 内的交互体验、代码审查质量或产品理解 |
| LiveBench | 强调较新的、持续更新的题目，用于降低训练数据污染，覆盖推理、编码、数学、语言等 | 中高：适合看“近期泛化状态”和避免只看陈旧题库 | 仍多是受控问题，不能替代长时 Agent 执行评测 |
| GPQA Diamond | 生物、物理、化学的高难度研究生/博士级四选一推理题 | 中：可作为严谨推理与“不会轻易瞎答”的信号 | 不等于能写出可靠技术方案、查对资料或完成业务分析 |
| AIME / HMMT 等数学题 | 竞赛数学、多步精确推理 | 低到中：对于算法、形式化逻辑、复杂计算有辅助意义 | 不等于工程能力、知识工作质量或 office 自动化效果 |
| MMMU / MMMU-Pro | 多学科、图文混合的理解与推理 | 中：若经常处理截图、表格、图表、设计稿、报告 PDF，会更有参考意义 | 不代表视觉生成质量，也不保证图表中的微小数值可靠 |
| BFCL | 根据自然语言正确选择工具/API、填对函数参数、处理多轮 function calling | 很高：如果你使用 MCP、Claude Code、Codex、浏览器/数据库/Notion/GitHub 工具链，这是关键基础能力 | 高分不保证 Agent 有好规划、会恢复失败、能完成长期任务 |
| WebArena / BrowserGym / 浏览器 Agent 类 | 在网页环境完成检索、填写、导航、跨页面操作等 | 中：适合调研、后台运营、网页办公和浏览器自动化 | 很受浏览器环境、网页变动和工具实现影响 |
| Chatbot Arena / 人类偏好榜 | 人类盲测更偏好哪个回答，覆盖对话体验、表达、风格等 | 中：适合初步看中文表达、互动感、回答组织能力 | 高 Elo 不等于代码正确、不等于事实可靠、更不等于 Agent 成功率 |

例如，GPQA Diamond 是从 GPQA 中筛出的 198 道高质量高难度四选一科学题；题目由相关领域专家设计，原始 GPQA 覆盖生物、物理、化学。它衡量的是高难科学推理，而不是“知识工作者日常写报告的准确性”。 [arxiv](https://arxiv.org/abs/2311.12022)

而 BFCL 测的是模型是否能根据指令选择并正确调用函数/API，包括工具调用的参数、格式和多轮处理。对于 MCP、GitHub、Notion、数据库、浏览器等 Agent 工作流，它往往比纯数学分数更有行动层面的意义。 [proceedings.mlr](https://proceedings.mlr.press/v267/patil25a.html)

## 你应优先看什么

以你的典型场景——Python/TypeScript 开发、Claude Code/Codex、Git/worktree、测试与质量门禁、Markdown/报告/内容工作流——我建议你把公开指标按以下优先级解读。

### Coding 与 Agent 开发

优先顺序：

1. **SWE-bench Pro 或更难、更近期的软件工程评测**
2. **SWE-bench Verified**
3. **Terminal-Bench**
4. **BFCL / 工具调用评测**
5. 长上下文、repo-level、multilingual coding 的具体子项
6. HumanEval、MBPP 等小函数生成题，仅作低权重参考

为什么不应只看 HumanEval 之类的“小函数题”？因为它更像“给定明确题目，补一个函数并通过单元测试”。而你日常真正痛的通常是：

- 找到该改哪个模块；
- 读懂隐含约束和已有实现；
- 在多个文件之间维持一致性；
- 不破坏旧行为；
- 编写、补充或修正测试；
- 在执行失败后自己定位、回滚、再次尝试；
- 按仓库规范提交合理、可审查的 diff。

SWE-bench 的优势在于它确实要求模型在真实仓库与真实 issue 语境中完成补丁，并靠测试行为而非答案文本相似度判定成功。 但它的局限也要记住：现实中用户给 Agent 的请求常常比 GitHub issue 更零碎、更口语、上下文更不完整；有研究指出，这种任务表达差异会明显影响评测与真实 IDE 使用表现之间的对应关系。 [qaskills](https://qaskills.sh/blog/swe-bench-explained-guide-2026)

**实操判断：**

- 如果目标是“能不能在 Claude Code 中稳定干活”，看 `SWE-bench + Terminal-Bench + BFCL` 的组合。
- 如果目标是“能不能独立接手较复杂 feature”，给 `SWE-bench Pro/长程工程任务` 更高权重。
- 如果目标是“在中文仓库、中文 issue、中文业务描述下是否可用”，必须自己测；英文开源 benchmark 不能替代。
- 如果你常接三方模型到 Claude Code，单独看模型卡分数不够，必须测“该 Provider 的实际 API、限流、上下文、工具协议兼容、长任务稳定性”。

### 知识工作与办公

对于研究、方案、文档、需求分析、会议纪要、报告、内容整理，建议不要把 GPQA/AIME 当作主指标。

更有用的公开信号是：

- **长上下文与文档理解**：模型能否基于长规格、多个文件、表格与资料做一致总结。
- **MMMU/多模态理解**：如果经常看产品截图、数据图、UI、PDF、表格和图片。
- **工具调用/BFCL**：如果任务通过搜索、知识库、Notion、Drive、数据库、日历或自动化工具完成。
- **事实性与引用能力的实际体验**：这几乎必须放到私有评测，因为不同产品是否联网、检索质量、引用展示方式、来源可追溯性差异极大。
- **结构化输出遵从性**：如 JSON、Markdown 模板、PRD、测试计划、测试用例、Mermaid、CSV 等。

你的真实办公任务通常不是“回答一道百科知识题”，而是：

> 把 10 份散乱资料整理成一份决策文档，并明确区分事实、假设、风险、待确认项，同时保留来源和可执行的下一步。

这类能力由检索、上下文组织、指令遵从、结构化输出、事实校验意识与工具链共同决定，公共单一榜单很难完整覆盖。

### 最小可用筛选矩阵

如果每次看到厂商发布一堆成绩，你可以只做这个快速判断：

| 你的用途 | 首看 | 次看 | 低权重或可忽略 |
|---|---|---|---|
| 日常 AI 编程、修 bug、改 repo | SWE-bench Pro、SWE-bench Verified | Terminal-Bench、长上下文、工具调用 | AIME、纯聊天榜 |
| Claude Code/Codex Agent 工作流 | Terminal-Bench、BFCL、SWE-bench | 可控性、长任务稳定性、成本/延迟 | 单轮代码补全分数 |
| 测试设计、代码审查、质量门禁 | 真实仓库修复与测试类成绩 | 推理、长上下文、结构化输出 | 纯前端视觉/竞赛数学 |
| 调研、写作、报告、PRD | 长文档理解、工具调用、多模态 | 人类偏好榜、引用能力实测 | SWE-bench |
| 表格、图表、截图、UI 评审 | MMMU/视觉理解类 | 长上下文、结构化输出 | 仅文本推理分数 |
| MCP/自动化/多工具 Agent | BFCL | Terminal-Bench、浏览器 Agent 评测 | Chatbot Arena 单一排名 |

## 建一套个人评测机制

你已经有“实现 Agent 与评审 Agent 分离”的质量意识，这正适合用到模型评估：**执行模型不能给自己判卷**。尽量让另一模型家族、脚本验证器或人工复核承担评分。

推荐你建立一个轻量但长期有效的 **Personal Model Eval Harness**。先别追求 1000 题，而是从 20–40 个高价值、可复跑任务开始。

### 第一步：按真实任务建题库

题目不应来自你“想象中会用的任务”，而应来自过去 1–3 个月你真实完成过、并且能判断好坏的任务。可以匿名化、去除敏感代码与客户信息后沉淀。

建议初版分为 5 类，总计 30 题：

| 任务桶 | 建议题数 | 你的题目例子 | 自动/人工判定 |
|---|---:|---|---|
| Repo 开发与修复 | 8 | 修复一个失败测试、实现一个明确小 feature、跨文件重构 | 测试通过、lint、type check、diff 审查 |
| 测试与质量保障 | 6 | 从需求生成边界测试、审查 PR 漏洞、补回归测试 | 覆盖的风险点、可执行性、专家盲审 |
| Agent 工具执行 | 5 | 查 repo、生成变更计划、执行命令、整理 Git 状态、失败恢复 | 任务是否完成、命令安全、工具调用正确率 |
| 知识与办公输出 | 6 | 资料整理、需求拆解、周报、技术调研、决策 memo | 事实正确性、溯源、结构、遗漏率 |
| 格式与内容生产 | 5 | 按固定模板出 Markdown、JSON、测试计划、公众号/XHS 文案框架 | Schema 校验、格式符合率、人工偏好 |

每个题目应当有一个**任务卡**，最少包含：

```yaml
id: coding-007
task_type: repo_bugfix
business_value: high
prompt: |
  当前仓库中 xxx 测试失败。请定位原因，修复实现，
  新增必要测试，并说明修改范围与风险。
inputs:
  repo_commit: abc123
  files_or_docs: [...]
allowed_tools:
  - bash
  - read_file
  - edit_file
success_criteria:
  - 新增失败测试变为通过
  - 原有测试全部通过
  - lint/typecheck 通过
  - 不修改无关模块
  - 最终说明包含假设和风险
scoring:
  correctness: 40
  regression_safety: 20
  test_quality: 15
  scope_control: 10
  explanation: 10
  tool_safety: 5
```

题目要有难度梯度：

- **L1：明确、短上下文、单文件或少量文件**
- **L2：含歧义、多文件、需查资料/查仓库**
- **L3：跨模块、长上下文、需要计划—执行—验证—修复闭环**
- **L4：开放任务，需要主动澄清、提出方案、识别风险、处理失败**

不要只测 L1。因为几乎所有前沿模型在“写一个函数”上都很漂亮，而你真正会感受到差异的地方，集中在 L2–L4。

### 第二步：定义评分，不只看“成功/失败”

对于编程任务，建议采用 100 分制，并区分硬门槛与软质量。

**硬门槛：一票否决或上限限制**

- 代码不可运行、测试未通过：总分上限 40。
- 破坏既有行为或引入明显安全问题：总分 0–20。
- 修改范围失控、删除测试绕过问题：总分 0。
- 无法按指定格式输出或工具调用失败：按场景设为失败或重扣分。
- 虚构已执行测试、虚构文件内容、虚构引用：重扣，且计入可靠性维度。

**软评分：用于区分“能做”与“值得长期用”**

| 维度 | 建议权重 | 怎样判 |
|---|---:|---|
| 任务正确性 | 30 | 是否真正满足需求、解决根因，而不是碰巧过测试 |
| 验证与回归安全 | 20 | 是否写/更新测试，是否运行必要校验，是否保护边界情况 |
| 需求理解与计划 | 10 | 是否识别约束、歧义、依赖、影响面 |
| 代码质量与范围控制 | 10 | diff 是否最小合理、风格一致、无无关改动 |
| 工具使用与自主恢复 | 10 | 是否正确用命令/工具，失败后是否定位并修复 |
| 可靠性与诚实性 | 10 | 不编造执行结果；不确定时明确说不确定；能提出澄清问题 |
| 效率与成本 | 10 | 耗时、token、调用次数、人工介入次数 |

而对知识工作/办公类任务，可使用另一套 100 分维度：

| 维度 | 建议权重 | 关注点 |
|---|---:|---|
| 事实正确与可溯源 | 25 | 关键结论有来源；不把猜测写成事实 |
| 任务覆盖完整度 | 20 | 是否回答了所有子问题、处理了限制条件 |
| 推理与判断质量 | 15 | 结论是否有依据、是否能比较取舍 |
| 结构与可执行性 | 15 | 文档是否可直接交付、下一步是否清楚 |
| 格式遵从 | 10 | 模板、Markdown/JSON、标题层级、字段约束 |
| 不确定性管理 | 10 | 明确假设、风险、待验证项 |
| 效率与成本 | 5 | 时间、模型成本、返工量 |

你可以把每个任务的最终分数定义为：

\[
\text{TaskScore}
=
\text{HardGate}
\times
\left(
0.30C + 0.20V + 0.10P + 0.10Q + 0.10A + 0.10R + 0.10E
\right)
\]

其中：

- \(C\)：Correctness，正确性；
- \(V\)：Validation，验证与回归安全；
- \(P\)：Planning，需求理解与计划；
- \(Q\)：代码/交付质量；
- \(A\)：Agent 执行与工具能力；
- \(R\)：可靠性与诚实性；
- \(E\)：效率成本；
- `HardGate`：通常为 0、0.4、0.8 或 1，用于体现“没跑通不能被文笔掩盖”。

### 第三步：按工作价值加权

不要让“生成一段文案”与“修复生产级测试失败”各占同样权重。应根据你的真实时间分布、风险和业务价值设权重。

一个适合你的起始权重可能是：

| 场景 | 总权重 |
|---|---:|
| Repo 开发、Debug、重构 | 35% |
| 测试设计、审查、质量门禁 | 20% |
| Agent 工具协作与终端工作 | 15% |
| 技术调研、方案、文档、数据整理 | 15% |
| 内容生产与固定格式交付 | 10% |
| 多模态/UI/图表理解 | 5% |

总分计算：

\[
\text{ModelScore}
=
\sum_{b=1}^{n} w_b \times
\frac{\sum_{i \in b} v_i \times s_i}{\sum_{i \in b} v_i}
\]

其中：

- \(w_b\)：任务桶权重；
- \(v_i\)：第 \(i\) 题的业务价值/风险权重，例如 1、2、3；
- \(s_i\)：标准化后的题目分数。

这里有一个重要原则：**不要用单一总分做所有决策。**

更好的输出形式是“模型角色画像”：

| 模型 | 主力开发 | 代码审查 | 长程 Agent | 文档研究 | 格式输出 | 成本效率 | 推荐角色 |
|---|---:|---:|---:|---:|---:|---:|---|
| 模型 A | 91 | 84 | 78 | 86 | 92 | 62 | 高风险实现、关键方案 |
| 模型 B | 82 | 90 | 83 | 80 | 87 | 78 | 独立审查、测试与反证 |
| 模型 C | 76 | 72 | 68 | 84 | 89 | 94 | 批量文档、初稿、低风险任务 |

这比宣布“模型 A 97.3 分第一名”更符合工作流现实。你可以让不同模型担任不同角色，而非强迫一个模型统治所有任务。

### 第四步：控制实验变量

模型比较最常见的错误是：你以为测的是模型，实际测到的是不同提示词、不同工具、不同上下文、不同 Agent 版本。

最少控制以下变量：

- **模型版本与 Provider**：记录确切 model ID、API Provider、日期。相同名字在不同平台可能不是同一版本、同一限额或同一上下文策略。
- **Agent 版本**：Claude Code、Codex、MCP 配置、插件、系统提示、skills 都要锁定版本。
- **工具权限**：是否允许联网、终端、写文件、测试、Git 命令、浏览器；不同模型必须对等。
- **任务上下文**：使用同一个 repo commit、同一份资料、同一初始目录状态。
- **预算**：最大轮数、最大 token、最大耗时、并行数。
- **提示策略**：要么统一 prompt，要么明确比较“每个模型可发挥的最佳实践 prompt”；两者是不同实验。
- **采样次数**：有随机性的任务至少跑 3 次，不应因单次偶然成功/失败定结论。

建议保留两条赛道：

- **标准赛道**：所有模型使用同一 Agent、同一 prompt、同一工具和预算。回答“基础能力谁更稳”。
- **生产赛道**：允许给不同模型采用其最佳实践，例如不同系统提示、不同 Agent scaffold、不同模型分工。回答“我的实际工作流该怎么配”。

标准赛道适合公平比较；生产赛道才适合真实部署。

## 消融实验是什么

“消融实验”（ablation study）来自实验科学与机器学习研究。它的核心不是“多跑几组对比”，而是：

> 在其他条件尽量不变的前提下，**有计划地移除、关闭、替换或简化一个组件**，观察结果变化，以估计这个组件究竟贡献了什么。

“消融”原意是去掉一部分；在模型/Agent 评测中，就是把系统的一块能力暂时拿掉。

例如你的编码 Agent 可能包含：

\[
\text{Agent}
=
\text{Base Model}
+
\text{System Prompt}
+
\text{Planning}
+
\text{Repo Search}
+
\text{Bash}
+
\text{Test Loop}
+
\text{Memory/Skill}
+
\text{Reviewer}
\]

如果完整系统在私有 coding 集上成功率为 78%，你不能立刻说“模型很强”。可能真正的增益来自测试循环、repo search 或 reviewer。消融的目的是分别估算这些模块的影响。

### 一个贴近你工作流的例子

假设你要评估一套“Claude Code + 自定义 Skill + 测试门禁 + 审查模型”的开发流程，可以设计：

| 实验组 | 规划 | Repo 搜索 | 自动测试循环 | 自定义 Skill | 独立审查 Agent | 想回答的问题 |
|---|---|---|---|---|---|---|
| Baseline | 否 | 基础 | 否 | 否 | 否 | 纯模型/基础 Agent 能力 |
| Full | 是 | 是 | 是 | 是 | 是 | 全系统最终生产表现 |
| - Planning | 否 | 是 | 是 | 是 | 是 | 计划步骤有没有贡献 |
| - Search | 是 | 否 | 是 | 是 | 是 | 仓库检索是否关键 |
| - Test Loop | 是 | 是 | 否 | 是 | 是 | 自动验证和失败恢复的价值 |
| - Skill | 是 | 是 | 是 | 否 | 是 | 你的 SOP/Skill 是否真有提升 |
| - Reviewer | 是 | 是 | 是 | 是 | 否 | 独立评审对质量门禁的贡献 |
| Reviewer same-family | 是 | 是 | 是 | 是 | 同家族模型 | 不同模型家族能否降低确认偏误 |

每组都跑同一批任务、同一代码版本、同一预算，至少重复若干次。最后比较：

- 成功率；
- 质量分；
- 平均时长；
- token/成本；
- 人工接管次数；
- 严重错误率；
- 虚构执行/误报测试通过率。

例如：

| 组别 | 任务成功率 | 平均质量分 | 平均耗时 | 人工接管 | 严重回归 |
|---|---:|---:|---:|---:|---:|
| Full | 78% | 86 | 12 分钟 | 0.35 次/题 | 3% |
| - Test Loop | 63% | 71 | 8 分钟 | 0.92 次/题 | 11% |
| - Skill | 71% | 79 | 13 分钟 | 0.52 次/题 | 5% |
| - Reviewer | 77% | 76 | 11 分钟 | 0.34 次/题 | 10% |

这种结果的解释就很具体：

- 自动测试循环把成功率提高了约 15 个百分点，同时显著降低回归风险；
- Skill 有正向贡献，但带来了少量额外耗时；
- reviewer 对“一次完成率”可能帮助不大，但对阻断严重回归更重要；
- 不能只看成功率，必须同时看风险与人工成本。

## 消融实验的常见误区

### 一次只改一个关键变量

如果你同时关闭“规划 + 搜索 + 测试”，结果变差了，你只知道“这三个一起有用”，不知道究竟是谁贡献最大。初学阶段优先使用 **one-factor-at-a-time**：每次仅改一个变量。

但也要知道组件之间会有交互：

- 没有 repo search，planning 的价值可能下降；
- 没有 test loop，强模型的优势可能被掩盖；
- 更严格的 reviewer 可能降低表面成功率，却提升长期质量。

当样本足够多，再补少量组合消融，例如 `- Planning - Search`，用于观察交互效应。

### 不把成本纳入结果

更复杂的 Agent 不一定更值得用。

假设 Full 系统把成功率从 72% 提高到 76%，但每题成本从 0.50 美元升到 5 美元、耗时从 8 分钟升到 30 分钟，那它可能只适合高风险任务。可增加一个简化效用指标：

\[
\text{Utility}
=
\text{QualityScore}
-
\lambda_c \times \text{Cost}
-
\lambda_t \times \text{Time}
-
\lambda_r \times \text{Risk}
\]

这里的 \(\lambda\) 不需要“科学真理”式精确，它只是把你的偏好显式化：

- 修生产 bug：把风险权重设得很高；
- 批量生成初稿：把成本和速度权重设得高；
- 技术方案与关键 PR：质量、可验证性、审查质量更重要。

### 把一次结果当成结论

LLM 输出有随机性。若每组只跑一次，差异可能只是偶然。对于昂贵的 Agent 测试，务实方案是：

- 高价值任务：每个模型/配置跑 3 次；
- 随机性极高或差异很小的任务：跑 5 次；
- 记录平均分、最好/最差结果、标准差；
- 如果模型 A 平均只高 1 分、但波动很大，不要据此迁移主力工作流。

### 用同一模型既生成又裁判

如果一个模型自己写代码、自己说“测试应该通过”、自己给自己高分，得到的是确认偏误，不是评估。

更可靠的判定顺序：

1. **优先机器验证**：单测、e2e、lint、type check、schema validator、diff/安全扫描。
2. **再用独立评审模型**：最好使用不同模型家族、不同供应商。
3. **最后人工抽检**：尤其是高风险、安全、架构、事实性和业务语义。

BFCL 之类工具调用评测之所以有价值，是因为它把“模型有没有正确发起函数/API 调用”变成了相对可验证的任务，而不是纯主观偏好。 [proceedings.mlr](https://proceedings.mlr.press/v267/patil25a.html)

## 建议的落地节奏

### 第 1 周：做最小题库

- 从最近真实项目里挑 20 个任务。
- 重点优先沉淀那些你曾经返工、被模型坑过、花最多人工审查时间的任务。
- 每题写清楚输入、允许工具、成功标准、禁区与评分方式。
- 先做 10 个 coding/QA 题、5 个 Agent/终端题、5 个知识办公/格式题即可。

### 第 2 周：跑基线

- 选 3–5 个你当前最常用或最关注的模型。
- 使用同一套 Agent、同一套 prompt、同一预算。
- 每题至少跑 1 次；关键题跑 3 次。
- 记录：成功、失败类型、耗时、token/费用、人工接管、严重问题。

失败类型建议强制编码，之后会非常有价值：

- `R1`：需求理解错；
- `R2`：仓库定位失败；
- `R3`：实现逻辑错误；
- `R4`：测试不足或回归；
- `R5`：工具调用/环境操作失败；
- `R6`：长上下文遗忘或偏题；
- `R7`：格式违约；
- `R8`：事实幻觉/虚构执行；
- `R9`：成本、限流、超时或服务不稳定。

### 第 3 周：做 3 个高价值消融

不要一下做十几组。先验证你最关心的三件事：

1. 自定义 Skill/SOP 到底是否比普通提示词有效？
2. 自动测试—修复闭环是否值得增加成本？
3. 独立 reviewer 是否真的减少回归与漏测？

你很可能会发现：模型之间的差距固然存在，但**任务定义、测试门禁、工具权限、上下文管理和审查机制**造成的差距，经常不亚于换一个榜单第一的模型。

### 长期维护

- 每月新增 2–5 个真实失败案例，形成“回归集”。
- 每次更换模型版本、Provider、Agent 版本或关键 Skill 后，至少跑一次核心回归集。
- 题目分为公开可共享、内部匿名、私有敏感三层。
- 把模型结果看成时间序列，不看成永久排名。
- 为每个模型定义“允许承担的任务等级”，而不是只定义“总分”。

例如：

- 80 分以上、回归风险低：可作为主力实现 Agent，但关键 PR 仍需审查。
- 70–80 分：适合中风险任务、测试生成、文档、辅助实现。
- 60–70 分：适合头脑风暴、初稿、批处理与低风险脚本。
- 任意总分但可靠性低：不要用于自动提交、删除、发布、生产变更。

## 最后的判断框架

看到下一次模型发布时，可以按下面顺序处理：

1. **看任务相似性**：榜单的输入、工具、环境、成功标准，像不像你的工作？
2. **看测的对象**：这是裸模型，还是模型加 Agent scaffold 的系统分数？
3. **看数据与协议**：题目是否陈旧、是否可能污染、预算和工具是否公平？
4. **看分数意义**：它是准确率、任务解决率、pass@1、pass@k，还是人类偏好？
5. **做私有复测**：用你的关键任务集验证。
6. **看稳定性与总成本**：不要只看最好的一次；看失败模式、人工接管和返工。
7. **用消融找真正杠杆**：确认收益来自模型本身、Skill、测试循环、检索、Reviewer，还是仅仅来自更多 token 和时间。

对你的场景，一个很实用的结论是：公开榜单里优先跟踪 **SWE-bench 系列、Terminal-Bench、BFCL、长上下文/多模态理解**；GPQA、AIME 等用于观察推理上限，但不应主导工具型知识工作与软件工程选型。然后用你的真实 repo、测试门禁、SOP/Skill、中文需求与办公交付标准，建立小而精、持续演化的私有评测集，最终把“谁在公开榜单第一”转化为“谁在我的工作流中最可靠、最省返工、最值得付费”。
