## 前缀匹配的三条核心规则

**规则一:写入只发生在断点位置,而且是累积哈希。** 给某个内容块打上 `cache_control`,系统只在这一个位置写一条缓存记录——这条记录的哈希值是从最开头到这个断点为止所有内容的累积哈希,不会在更早的位置额外写记录。这意味着断点之前任何一个块发生变化,断点处算出来的哈希就会变,下次请求直接判定为"没找到"。 [platform.claude](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

**规则二:读取是往回找"别人写过的记录",不是找"内容稳定的地方"。** 每次请求会先在断点位置算哈希、查有没有匹配的缓存;如果没有,系统会一个块一个块往回走,检查更早的位置是否有匹配的记录——但它只认"之前请求真的在那个位置打过断点、写过缓存"的地方,不会因为某段内容"看起来没变"就凭空认定它可复用。这是最容易被误解的一点:**内容稳定不等于会被命中,必须在稳定的边界上主动放一个断点**。

**规则三:往回查找的窗口只有 20 个块。** 超过 20 个位置还没找到匹配,查找就停止(除非你设了第二个断点,从那里重新开一个 20 块的查找窗口)。有个细节对写代码/工具调用场景很友好:一连串的 `tool_use` 块算一个位置,一连串的 `tool_result` 块也算一个位置,所以一轮里并行调用很多工具,不会把上一轮的缓存记录一下子挤出这个 20 块窗口。

## 层级顺序决定了"改哪里,坏多远"

缓存前缀按 `tools → system → messages` 的顺序构建，形成一个层层叠加的层级结构。**改动越靠前，波及范围越大**：

| 改动内容 | 工具缓存 | 系统缓存 | 消息缓存 | 说明 |
|---|---|---|---|---|
| 工具定义(名称/描述/参数) | 失效 | 失效 | 失效 | 波及全部,代价最大 |
| 开关联网搜索/引用功能 | 保留 | 失效 | 失效 | 因为改动了 system prompt |
| 切换 speed 档位 | 保留 | 失效 | 失效 | 同上 |
| `tool_choice` 参数 | 保留 | 保留 | 失效 | 只影响消息层 |
| 增删图片 | 保留 | 保留 | 失效 | 只影响消息层 |
| thinking/effort 配置变化 | 视模型而定 | 视模型而定 | 失效 | 这两个参数会被渲染进提示词里 |

**这条规律直接指导实践**：如果你要频繁调整某个东西（比如每天更新一次的背景资料），千万别把它和几乎不变的工具定义、system 指令混在一起放在同一层,应该单独用一个断点隔离出来,这样调整它时不会连累前面更稳定的部分。

## 断点放置的实操技巧

**技巧一:断点必须打在"跨请求完全相同"的最后一个块上,而不是打在最后一个块本身。** 文档专门举了一个"常见错误"的例子:如果提示词结构是"大段静态内容(块1-5)+ 每次请求都带时间戳的可变块(块6)",却把断点打在块6上——那么每次请求块6的哈希都不同,往回查找会经过块5、4、3、2、1,但这些位置从来没被写过记录,于是**永远只写入、永远读不到命中**。正确做法是把断点挪到块5,也就是最后一个稳定块的末尾。**自动缓存模式也会踩这个坑**,因为它默认把断点放在最后一个可缓存块上——如果这个位置恰好是易变内容,就必须改用显式断点手动指定位置。

**技巧二:最多可以设 4 个显式断点,用来隔离不同变化频率的区块。** 比如工具定义几乎不变、背景资料每天更新、对话历史逐轮增长——三者变化频率不同,分别打断点,一处改动就不会拖累另外两处。

**技巧三:多断点还能应对"对话长到超出 20 块窗口"的情况。** 如果单靠一个不断后移的断点,一旦某一轮新增的块数把它推出 20 块回溯窗口,就会突然全部 miss;这时额外在中段固定打一个断点,相当于给回溯开了第二个入口,避免长对话中途"断崖式"失效。

**技巧四:精确匹配要求逐字节相同,包括图片。** 断点覆盖的所有文本和图片内容必须与之前写入时 100% 一致,哪怕是 JSON key 顺序被某些语言(比如 Swift、Go)在序列化时随机打乱,都会导致匹配失败——这是排查"明明没改内容却总 miss"问题时最容易忽略的一点。

**技巧五:有最低长度门槛,低于门槛的内容不会报错但也不会被缓存。** 门槛因模型而异,大多在 1024~4096 token 之间;如果你的静态内容刚好卡在门槛边缘,适当把它撑大反而更划算,因为读缓存的价格只有基础价的十分之一。

**技巧六:混用 1 小时和 5 分钟 TTL 有顺序要求。** 长 TTL 的断点必须出现在短 TTL 断点之前,不能反过来,系统会依次计算三个计费分界点分别按缓存命中价、1 小时写入价、5 分钟写入价结算。

**技巧七:可以用"预热"消除首次请求的冷启动延迟。** 设置 `max_tokens: 0` 发一个不产生任何输出的空跑请求,专门用来把 system prompt 或工具定义提前写进缓存,断点要打在和后续正式请求共享的最后一个稳定块上,而不是打在预热用的占位消息上，否则预热写入的记录压根匹配不上真实请求。

## 和你之前几轮问题的衔接

结合你关心的 Claude Code cold cache 问题：Claude Code 采用的正是"自动缓存"模式,断点随对话增长自动后移，这就是为什么第三方中转网关如果**剥离或改写了请求里的时间戳、attribution header 之类的易变字段位置**，很容易意外把断点卡在错误的位置上，导致明明内容大部分没变，却总是全量重算——这本质上就是这里说的"技巧一"那个常见错误的变种。
